# V0.3 Execution Orchestration

## Purpose

This document describes how a job moves from the FastAPI interface through the V0.3 execution platform into the V0.2 synthetic-data engine.

## Execution Flow

```text
Client
  |
  v
FastAPI
  |
  v
JobService
  |
  +----> SQLite job metadata
  |
  v
In-memory JobQueue
  |
  v
Background Worker
  |
  v
Execution Adapter
  |
  v
V0.2 Engine
  |
  v
V0.2 Pipeline
  |
  v
CSV + Evaluation Report
  |
  v
Job status and artifacts
```

Jobs can be submitted through either the JSON-based job endpoint or the multipart upload endpoint:

- `POST /api/v1/jobs`
- `POST /api/v1/jobs/upload`

The JSON endpoint accepts a server-accessible input CSV path. The upload endpoint accepts a client-provided CSV and a requested output row count.

## Failure Flow

```text
Background Worker
  |
  v
Execution Adapter
  |
  v
V0.2 Engine
  |
  v
Execution or validation error
  |
  v
JobService records failure
  |
  v
FAILED
```

Errors are recorded against the job using the platform's error-handling model. API responses should not expose internal stack traces or sensitive dataset values.

## Runtime Architecture

V0.3 uses an in-memory FIFO job queue. The API and background worker operate within the same application process.

SQLite persists job metadata and lifecycle state. The queue itself is not durable, so queued work is not automatically preserved by the queue across a process restart. Job artifacts are stored on the local filesystem.

This is a local, single-instance execution design, not a distributed worker architecture.

## Startup Recovery

At startup, the platform reconciles persisted job states:

- Queued jobs with an existing input file can be re-enqueued.
- Queued jobs whose input file is missing are marked failed with `INPUT_FILE_MISSING`.
- Jobs persisted as `RUNNING` are marked failed with `STALE_JOB` rather than automatically retried.

Startup recovery assumes exclusive ownership of the SQLite database by one application instance during recovery. Multiple instances sharing the same database are not safe without additional ownership or lease coordination.

A process interruption may leave partial artifacts on disk. Automatic retries and general partial-artifact cleanup are not guaranteed.

## Responsibilities

### FastAPI

- Exposes HTTP endpoints.
- Validates request data.
- Creates jobs and serves job status.
- Provides artifact listing and download routes.
- Exposes health, version, and readiness information.

### JobService

- Creates and validates jobs.
- Coordinates job lifecycle transitions.
- Persists job metadata.
- Dispatches eligible jobs to the queue.
- Records execution outcomes.

### JobQueue

- Dispatches jobs using an in-memory FIFO queue.
- Does not provide durable queue storage.

### Background Worker

- Consumes queued job identifiers.
- Coordinates execution.
- Updates job lifecycle state to success or failure.

### Execution Adapter

- Retrieves the persisted job.
- Passes the input CSV path and requested row count to the V0.2 engine.
- Adapts engine results for the worker execution contract.

### V0.2 Engine

- Runs the existing synthetic-data pipeline.
- Performs ingestion, profiling, identifier handling, metadata preparation, and synthetic generation.
- Validates output schema.
- Evaluates statistical quality and privacy risk.
- Persists generated artifacts and the evaluation report.

## Job Lifecycle

The normal successful path is:

`CREATED` -> `QUEUED` -> `RUNNING` -> `SUCCEEDED`

The execution failure path is:

`RUNNING` -> `FAILED`

A queued job may also fail before execution completes, for example if its input file is missing during startup recovery.

## API Endpoints

- `GET /api/v1/health` — health status.
- `GET /api/v1/version` — platform version.
- `GET /api/v1/readiness` — readiness status.
- `POST /api/v1/jobs` — create a job using an existing server-accessible CSV path.
- `POST /api/v1/jobs/upload` — upload a CSV and create a job.
- `GET /api/v1/jobs/{job_id}` — retrieve job status.
- `GET /api/v1/jobs/{job_id}/artifacts` — list job artifacts.
- `GET /api/v1/jobs/{job_id}/artifacts/{artifact_name}` — retrieve a specific artifact.

Successful jobs normally produce `synthetic_data.csv` and `report.json` under:

`data/output/jobs/{job_id}/`

## Security and Privacy Boundaries

The upload endpoint treats uploaded files as untrusted input and applies configured file, row-count, encoding, and CSV validation controls. Artifact access must remain confined to the relevant job's artifact directory.

V0.3 does not provide authentication, authorization, API keys, role-based access control, or tenant isolation. Do not expose this service to untrusted users as though those controls already exist.

Privacy evaluation is an engineering assessment, not a certification:

- Exact identifier matches result in `FAIL`.
- Missing protected identifier columns or detected synthetic duplicates require `REVIEW_REQUIRED` under the implemented evaluation rules.
- `PASS` does not establish legal or regulatory compliance and does not guarantee protection against every privacy attack.

## Architectural Constraints

V0.3 uses:

- FastAPI for the HTTP interface.
- SQLite for job metadata.
- An in-memory queue.
- A background worker within the application process.
- Local filesystem storage for input and output artifacts.
- The existing V0.2 engine for synthesis and evaluation.

V0.3 does not provide a durable external queue, distributed workers, horizontal scaling, production database orchestration, cloud object storage, or multi-table synthesis.

The V0.2 engine remains the processing core; V0.3 provides the execution platform around it.
