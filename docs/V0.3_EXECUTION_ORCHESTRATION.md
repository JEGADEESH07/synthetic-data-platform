Runtime Architecture

V0.3 uses an in-memory JobQueue. Therefore the API and worker share the same application process.

The worker runs in a background thread and continuously consumes queued jobs.

No external queue infrastructure is introduced in V0.3.

## Responsibilities

### FastAPI

* HTTP interface
* request validation
* job creation
* job status retrieval
* artifact retrieval

### JobService

* job creation
* lifecycle transitions
* persistence coordination

### JobQueue

* in-memory FIFO job dispatch

### Worker

* consumes queued jobs
* transitions jobs to RUNNING
* executes the configured executor
* transitions jobs to SUCCEEDED or FAILED

### Execution Adapter

* receives a job ID
* retrieves the persisted Job
* supplies job input\_file and row\_count to V02Engine
* converts V02Engine artifact results into the Worker executor contract

### V02Engine

* executes the unchanged V0.2 pipeline
* validates schema
* evaluates privacy
* persists generated artifacts

## Job Lifecycle

CREATED → QUEUED → RUNNING → SUCCEEDED

Failure:

RUNNING → FAILED

## Architectural Constraints

V0.3 does not introduce:

* Redis
* Kafka
* RabbitMQ
* Celery
* Kubernetes
* PostgreSQL production infrastructure
* distributed workers
* authentication
* multi-tenancy

The V0.2 engine remains unchanged.
