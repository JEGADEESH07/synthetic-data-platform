# V0.3 Execution Orchestration

## Purpose

Define how a submitted job moves from the FastAPI API through the V0.3 execution platform into the existing V0.2 synthetic data engine.

## Execution Flow

POST /api/v1/jobs
    ↓
JobService.create_job()
    ↓
JobService.queue_job()
    ↓
JobQueue.enqueue()
    ↓
Worker background thread
    ↓
Execution Adapter
    ↓
JobService.get_job()
    ↓
V02Engine.execute()
    ↓
V0.2 Pipeline
    ↓
Artifact persistence
    ↓
JobService.mark_succeeded()

## Failure Flow

Worker
    ↓
Execution Adapter
    ↓
V02Engine
    ↓
Exception
    ↓
JobService.mark_failed()
    ↓
FAILED

## Runtime Architecture

V0.3 uses an in-memory JobQueue. Therefore the API and worker share the same application process.

The worker runs in a background thread and continuously consumes queued jobs.

No external queue infrastructure is introduced in V0.3.

## Responsibilities

### FastAPI

- HTTP interface
- request validation
- job creation
- job status retrieval
- artifact retrieval

### JobService

- job creation
- lifecycle transitions
- persistence coordination

### JobQueue

- in-memory FIFO job dispatch

### Worker

- consumes queued jobs
- transitions jobs to RUNNING
- executes the configured executor
- transitions jobs to SUCCEEDED or FAILED

### Execution Adapter

- receives a job ID
- retrieves the persisted Job
- supplies job input_file and row_count to V02Engine
- converts V02Engine artifact results into the Worker executor contract

### V02Engine

- executes the unchanged V0.2 pipeline
- validates schema
- evaluates privacy
- persists generated artifacts

## Job Lifecycle

CREATED → QUEUED → RUNNING → SUCCEEDED

Failure:

RUNNING → FAILED

## Architectural Constraints

V0.3 does not introduce:

- Redis
- Kafka
- RabbitMQ
- Celery
- Kubernetes
- PostgreSQL production infrastructure
- distributed workers
- authentication
- multi-tenancy

The V0.2 engine remains unchanged.
