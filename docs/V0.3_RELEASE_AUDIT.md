# V0.3.1 Release Audit — Pre-release

## 1. Release Identity

Project: Synthetic Data Engineering & Privacy Platform

Target release: V0.3.1

V0.3.1 extends the V0.3 execution platform with controlled multipart CSV ingestion, additional validation and security tests, and documented startup-recovery behavior.

V0.2 remains the synthetic-data engine. V0.3 provides the API, job lifecycle, queue, worker, persistence, and artifact-management layer.

This document records verification evidence. It does not itself authorize a release.

## 2. Implemented API

- `GET /api/v1/health` — health status.
- `GET /api/v1/version` — platform version.
- `GET /api/v1/readiness` — readiness status.
- `POST /api/v1/jobs` — create a job using a server-accessible CSV path.
- `POST /api/v1/jobs/upload` — upload a CSV using multipart form data and create a job.
- `GET /api/v1/jobs/{job_id}` — retrieve job status.
- `GET /api/v1/jobs/{job_id}/artifacts` — list job artifacts.
- `GET /api/v1/jobs/{job_id}/artifacts/{artifact_name}` — retrieve an artifact.

## 3. Upload Boundary

The upload endpoint treats client-provided files as untrusted input.

Configured limits and validation include:

- Maximum upload size: 100 MB.
- Maximum input rows: 100,000.
- Maximum generated rows: 100,000.
- UTF-8 encoding validation.
- CSV validation and duplicate-column rejection.
- Symlink input restrictions.

The JSON-based job endpoint remains available for server-accessible CSV paths. Remote object-storage ingestion is not supported.

Use fictional or approved development datasets for local development. Do not store production customer datasets on a local development machine.

## 4. Architecture

The execution path is:

Client -> FastAPI -> JobService -> SQLite metadata and in-memory queue -> Background Worker -> Execution Adapter -> V0.2 Engine -> Artifacts and evaluation report.

SQLite stores job metadata and lifecycle state. The queue is in-memory and is not durable across process restarts. The worker runs within the application process. Artifacts use local filesystem storage.

The design is single-instance oriented and does not provide distributed worker coordination or horizontal scaling.

## 5. Startup Recovery

Startup recovery handles persisted jobs as follows:

- Queued jobs with existing input files can be re-enqueued.
- Queued jobs with missing input files are marked failed with `INPUT_FILE_MISSING`.
- Jobs left in `RUNNING` state are marked failed with `STALE_JOB`.

Automatic retries are not provided. Partial artifacts may remain after an interrupted job.

Recovery assumes exclusive ownership of the SQLite database during application startup. Multiple application instances sharing the same database are not safe without additional ownership or lease coordination.

## 6. Privacy Evaluation Boundary

Privacy evaluation is an engineering assessment, not a legal or regulatory certification.

Current status rules:

- Exact identifier matches: `FAIL`.
- No protected identifier columns: `REVIEW_REQUIRED`.
- Detected synthetic duplicates: `REVIEW_REQUIRED`.
- Otherwise, the implemented evaluator may return `PASS`.

A `PASS` result does not guarantee protection against every re-identification or inference attack and does not establish regulatory compliance.

## 10. Docker Verification

The Docker image `synthetic-data-platform:v0.3.1` was rebuilt and exercised through an upload-to-artifact workflow.

Recorded verification:

- Container startup.
- CSV upload and job creation.
- Successful job completion.
- Ten generated rows from a ten-row fictional input.
- Artifact listing and CSV download.
- Evaluation report retrieval and schema validation.

Verified job ID: `c19f891b-607d-431e-b693-ec111957d740`

The report recorded platform version `0.3.1`, engine version `0.2.0`, and SDV version `1.38.5`. The privacy status was `REVIEW_REQUIRED`, with zero exact matches and zero duplicate rows because no protected identifier columns were available.

The Docker test does not establish production readiness. Persistent storage depends on the actual mounted paths and database configuration; an in-memory queue remains non-durable.

## 11. Dependencies and Reproducibility

The project pins SDV to `1.38.5`. This is not a complete dependency lockfile.

The development environment uses Python 3.12. The Docker environment uses CPU-only PyTorch.

A seed and training configuration are recorded for reproducibility, but identical synthetic output across independent training runs is not guaranteed. Repeated same-seed tests passed during the recorded audit; that evidence is not a universal determinism guarantee.

## 12. Explicit Limitations

V0.3.1 does not provide:

- Authentication or authorization.
- API-key management or RBAC.
- Tenant isolation or multi-tenancy.
- Enterprise SSO.
- A durable external job queue.
- Distributed workers or horizontal scaling.
- Production database orchestration.
- Cloud object storage.
- Remote object-storage ingestion.
- Relational or multi-table synthesis.
- Legal, regulatory, or universal privacy certification.

Do not expose the service to untrusted users as though the missing access controls already exist.
