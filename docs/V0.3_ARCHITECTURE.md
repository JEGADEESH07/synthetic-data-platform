# V0.3 Architecture Specification

## 1. Purpose

V0.3 introduces a service and job-execution layer around the existing V0.2 Synthetic Data Engine.

V0.2 remains the core synthetic-data engine. V0.3 provides API access, job management, queueing, worker execution, persistence, and artifact retrieval.

## 3. V0.2 Engine Boundary

V0.2 remains unchanged.

The existing V0.2 pipeline entry point is:

    synthetic_data.pipeline.run_pipeline()

The V0.3 worker will call the existing V0.2 engine rather than reimplementing generation, evaluation, privacy, or pipeline logic.

## 4. V0.3 Components

### API

Responsible for HTTP requests, responses, API versioning, validation, and safe error responses.

Initial API namespace:

    /api/v1/

### Jobs

Responsible for the job domain, job creation, status management, persistence, and lifecycle.

### Queue

Responsible for holding jobs waiting for execution.

V0.3 uses a simple local queue. External queue infrastructure is intentionally out of scope.

### Worker

Responsible for executing queued jobs and invoking the V0.2 engine.

### Job Database

SQLite is used for V0.3 job-state persistence.

The database stores job metadata and lifecycle state, not generated CSV data.

### Artifacts

Generated files remain file-based artifacts.

Expected artifacts:

    synthetic_data.csv
    report.json

Artifacts are stored under:

    data/output/jobs/<job_id>/

## 7. Architectural Responsibilities

API:
- HTTP interface
- Request validation
- Response serialization
- Safe API errors

Job Service:
- Job creation
- Job lifecycle management
- Coordination between persistence and queue

Job Repository:
- Store and retrieve job state

Queue:
- Hold pending jobs

Worker:
- Execute jobs
- Invoke V0.2 engine
- Handle execution failures
- Persist results

V0.2 Engine:
- CSV ingestion
- Profiling
- Identifier detection
- Metadata policy
- Synthetic generation
- Identifier generation
- Validation
- Evaluation
- Privacy evaluation

Artifact Layer:
- Store synthetic CSV
- Store evaluation report
- Expose artifact locations

## 8. Error Boundary

Internal exceptions must not be exposed directly through the API.

API errors should use safe structured responses containing an error code and safe human-readable message.

Internal stack traces, filesystem paths, implementation details, and sensitive data must not be returned to API clients.

## 9. Logging

Job execution must be traceable using the job ID.

Important lifecycle events include:

- job created
- job queued
- job started
- engine execution started
- engine execution completed
- artifacts persisted
- job succeeded
- job failed

Sensitive dataset values must not be written to logs.

## 10. Technology Scope

V0.3 uses:

- Python 3.12
- FastAPI
- SQLite
- Local job queue
- Existing V0.2 engine
- Existing artifact persistence
- Docker
- Pytest

## 11. Explicitly Out of Scope

The following are not part of V0.3:

- Kubernetes
- Kafka
- Redis
- RabbitMQ
- PostgreSQL production deployment
- Authentication
- RBAC
- Billing
- Multi-tenancy
- Advanced relational synthesis
- Cloud deployment
- Enterprise SSO
- Production orchestration

## 12. Core Architectural Principle

V0.2 is the engine.

V0.3 is the execution platform around the engine.

The V0.3 service layer must call and reuse the V0.2 engine rather than duplicate its functionality.
